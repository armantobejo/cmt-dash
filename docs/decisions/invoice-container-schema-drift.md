# Decision: INVOICE.CONTAINERN production schema drift

Status: decided 2026-09-23 · Owner: engineering · Discovered during P2 live smoke

## The drift

The real company DBs (`data/CME.db`, `CMT.db`, `CSM.db`, `MAL.db`, `SBY.db` —
all five audited) have **no `INVOICE.CONTAINERN` column**, but both apps'
invoice-detail query selected it:

```
i.BLNO, i.BLNO3, i.CONTAINERN, i.PORTOFLOAD, i.PORTOFDISC,
```

Result: `GET /invoices/detail` returned **500 on real production data in both
apps** (the invoice *list* never selects it, so only the detail page broke).
Shipment detail kept working because its `u.CONTAINERN` comes from
`UnifiedShipment`, which does have the column.

## Options considered

1. **Add the column to the real DBs** — rejected. `tools/sync_db.py` **drops
   and recreates every table from the DBF's own field metadata** on every sync;
   the SQLite schema is dictated by FoxPro. Any hand-added column would be
   wiped by the next `/sync`, and pre-adding it would diverge the sync schema
   from the DBF contract it is generated from.

2. **Fix both apps' detail queries together** — chosen. The SELECT named a
   column that does not exist in the schema the sync produces; the correct fix
   is to stop selecting it in both ports at once, preserving parity by
   construction (single source of truth: `src/app/queries.py`, mirrored by
   `laravel/app/Support/CmtQueries.php`).

## What changed

- `src/app/queries.py::get_invoice_detail` — dropped `i.CONTAINERN` from the
  SELECT (commented why).
- `laravel/app/Support/CmtQueries.php::getInvoiceDetail` — same drop, same
  comment, so the ports cannot drift apart again silently.
- `laravel/resources/views/invoice_detail.blade.php` — `($header->CONTAINERN
  ?? null) ?: '-'`, mirroring Jinja's `Undefined or '-'` fallback. No Python
  template change was needed: `detail.header.CONTAINERN or '-'` already
  renders `-` for an undefined key.
- Parity baseline regenerated. Diff vs the previous baseline is exactly two
  steps (`invoices/detail_known`, `invoices/customer_own_detail`):
  `1x20` → `-`.

## Verification

- Python: 81/81 tests (incl. the 10 regenerated parity-baseline captures).
- Laravel: 62/62 tests.
- Live on real data (invoice `_7K70TXB4W`, CMT.db): Laravel `:8200` → 200,
  Python `:8000` (Docker, rebuilt image) → 200. Both render the Kontainer
  card as `-` with identical surrounding content.

## P3 note

If the business ever wants the invoice's container number back on the detail
page, the change must start at the DBF mapping (which FoxPro field, if any,
feeds it) — not at the SQLite schema.

## Enforcement (added 2026-09-23)

The regression class — tests passing against schemas **wider than reality** —
is now mechanically gated in both suites (wired into the parity checklist as
`meta.schema_gates` + feature F-06d step s5):

- **`tests/parity/fixtures/real_schema.json`** — committed snapshot of the
  real company DBs' column sets (all five DBs), regenerated by
  **`tools/dump_real_schema.py`**. The sync owns these schemas; tests must
  never widen them.
- **`tests/test_schema_gate.py`** (runs in the plain `pytest tests/` suite):
  1. fixture ≡ live `data/*.db` (hard gate where they exist; skip otherwise),
  2. parity dataset tables ⊆ production shape (caught a second phantom:
     `NA.TYPETRAN` — the unified view derives it as a literal, the real NA
     table never has it),
  3. every query function in `queries.py` executes against a
     production-shaped DB (rows from the parity dataset, columns from the
     fixture); a pinned test asserts invoice detail never selects
     `CONTAINERN` again.
- **`laravel/tests/Feature/ProductionSchemaTest.php`** — the same three gates
  for the PHP side (seed ⊆ production; every `CmtQueries` method executes on
  production shape; pinned `CONTAINERN` regression).
- Test schemas were aligned to reality too: the app-test conftest no longer
  ALTERs `INVOICE.CONTAINERN` into existence, and the parity dataset dropped
  its phantom columns (`INVOICE.CONTAINERN/PAY_USD/PAY_IDR`, `VESSEL.UNIK`,
  `NA.TYPETRAN`). Baseline regeneration diff: **empty** (behavior-neutral).

Rule of thumb the gates encode: **a query that only works because a test
invented a column is a production 500, not a pass.**
